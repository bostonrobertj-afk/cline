# Input Prompt Cleanup Requirements

## Purpose

This document defines the requirements for relocating runtime-generated prompt content out of request `input`/conversation history and into request `instructions`, while preserving all existing prompt behavior, gating, timing, and provider-specific configuration.

This is a relocation-only change.

It is not a prompt redesign.
It is not a behavior simplification.
It is not a semantic cleanup.

Anything that moves must continue to:

- appear on exactly the same turns where it appears today
- be omitted on exactly the same turns where it is omitted today
- preserve all existing contextual filtering and workflow-specific branching
- preserve all existing full-prompt vs continuation-turn behavior
- preserve all existing first-turn-only behavior
- preserve existing provider/tool configuration

## Core Requirement

System-generated prompting that is currently transported through request `input` must instead be transported through request `instructions`, unless this document explicitly marks that content as intentionally excluded.

The runtime meaning of the content must not change.
Only its transport location may change.

## Current-State Problem Statement

The runtime already distinguishes between:

- system prompt content transported through `instructions`
- conversation/history content transported through `input`

For OpenAI Responses-compatible paths, providers such as:

- [openai-native.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/api/providers/openai-native.ts:423)
- [openai-codex.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/api/providers/openai-codex.ts:176)
- [openai.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/api/providers/openai.ts:336)

already send the main system prompt through `instructions`.

However, the main task loop still appends several runtime-generated prompt blocks into conversation content before request assembly, causing them to be serialized as user/input messages by the shared Responses converter:

- [openai-response-format.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/api/transform/openai-response-format.ts:123)

That means runtime-generated prompt material is currently split across:

- `instructions`
- user/input messages

This update standardizes that transport so in-scope system-generated prompting is carried by `instructions`.

## Required Behavioral Invariants

Everything below is mandatory.

### 1. Relocation must preserve selection logic exactly

If a block is included today only when a specific condition is true, that exact condition must still control inclusion after relocation.

Examples:

- focus-chain instructions must continue using `shouldIncludeFocusChainInstructions()`
- placeholder activation must continue using its existing activation conditions
- compact-summary injection must continue using the current compaction path
- environment details must continue honoring detailed vs reduced modes

### 2. Relocation must preserve turn timing exactly

If a block appears:

- only on first turns
- only on full-prompt refresh turns
- on continuation turns
- on full-prompt turns but not continuation turns
- on every applicable internal turn

it must continue to appear on exactly those turns after relocation.

This is especially important for:

- placeholder-workflow activation instructions
- focus-chain/current-step guidance
- continuation-turn prompt behavior
- prompt-refresh-frequency behavior

### 3. Relocation must preserve contextual filters exactly

Existing contextual filters and dynamic prompt composition must continue unchanged.

This includes, but is not limited to:

- workflow-specific gating
- placeholder current-step resolution
- deterministic placeholder gating
- prompt-refresh gating
- managed-workflow branching
- model/provider-specific prompt-variant selection
- native tool schema contextual filtering
- minimal GPT prompt behavior

No prompt text may become unconditional merely because it moved into `instructions`.

### 4. Relocation must preserve prompt-section semantics

If content currently behaves like a runtime-generated prompt section, it must remain a prompt section after relocation, not become a synthetic user utterance.

This means the destination should be the request instructions/system-prompt path, not a fake `role: "system"` entry inside `input`.

### 5. Relocation must preserve provider compatibility

The resulting request shape must remain valid for:

- Responses-backed providers
- non-Responses providers
- providers using prompt variants
- providers using native tools

Nothing in this update may break prompt transport for providers that do not expose a top-level Responses `instructions` field, but the in-scope runtime-generated prompting must still stop riding as user/input content where the request architecture supports proper system/instructions transport.

## Architecture Requirements

## System Prompt Path

The relocation target is the existing system-prompt/instructions path.

The runtime already has a structured system-prompt pipeline through:

- [components/index.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/prompts/system-prompt/components/index.ts:22)
- [types.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/prompts/system-prompt/types.ts:89)

and provider adapters already know how to transmit the final system prompt through `instructions` where applicable.

The relocation must use that path rather than inventing a second ad hoc “instruction-like” message channel in `input`.

## No Fake System Messages In Responses Input

For Responses-backed providers, relocated prompt content must not be reintroduced as `input` items with:

- `role: "system"`

The OCA Responses path must be aligned with the standard top-level `instructions` shape.

## Preservation Of Existing Dynamic Context Assembly

The relocation must preserve all existing dynamic assembly sources.

This means existing builders/generators remain the source of truth, including:

- `getEnvironmentDetails(...)`
- `summarizeTask(...)`
- `buildPlaceholderWorkflowActivationInstructions(...)`
- `generateFocusChainInstructions()`
- `buildSubagentPromptInjectionBlocks(...)`

Those sources may be rerouted, but not semantically rewritten.

## Required Content Mapping

The following transport remapping must hold after implementation.

### Main task

These blocks must stop being appended into outbound user/input content:

- environment details
- summarize-task compact block
- placeholder activation instructions
- focus-chain instructions/current-step details

These blocks must instead be appended into the effective system prompt / instructions payload for the same turn.

### Subagents

These blocks must stop being appended into local conversation/input for ordinary prompt transport:

- placeholder activation instructions
- focus-chain/current-step guidance

They must instead be incorporated into the effective system prompt / instructions path while preserving their current turn-by-turn inclusion behavior.

The subagent workspace metadata block is excluded and must remain unchanged.

### OCA Responses

The OCA Responses provider must stop building:

- `input: [{ role: "system", content: systemPrompt }, ...]`

and must instead send:

- `instructions: systemPrompt`
- `input: ...non-system items only...`

## Existing Behavior That Must Remain Intact

The following current behaviors are explicitly required to remain unchanged.

### Main-task behavior

- The base system prompt must still be generated through `getSystemPrompt(promptContext)`.
- Prompt metadata artifact writing must continue to capture the effective system prompt.
- Token estimation must continue to reflect the actual system prompt sent.
- Context-compaction behavior must not change.
- Environment detail generation must still occur under the same detailed/reduced rules.

### Continuation-turn behavior

The continuation-turn prompt remains governed by the existing continuation infrastructure and selection rules.

Relevant files:

- [prompt-refresh.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/task/prompt-refresh.ts:48)
- [continuation_turn.ts](/Users/robertboston/Documents/Cline%20Extension/cline/src/core/prompts/system-prompt/components/continuation_turn.ts)

If an in-scope runtime block currently appears on continuation turns, it must continue to appear on continuation turns after relocation.

If an in-scope runtime block is currently absent on continuation turns, it must remain absent.

This requirement is especially explicit for focus-chain content:

- the focus-chain task list must continue to appear on continuation turns where it appears today
- the auto-completed workflow-step notice block must continue to appear on continuation turns where it appears today
- the placeholder-workflow current-step detail block, including `# CURRENT WORKFLOW STEP`, must continue to appear on continuation turns where it appears today
- after relocation, those continuation-turn appearances must be carried by the continuation-turn instructions path rather than by request input/conversation transport

The relocation must not accidentally make continuation turns lose:

- the rendered checklist block
- the current progress line
- the auto-completed workflow-step notice block
- the current-step detail block
- the reminder line currently associated with those focus-chain/current-step turns

### Prompt refresh behavior

- prompt injections belong in the system prompt rather than local user-message reinjection

## Non-Goals

- Do not change prompt wording.
- Do not merge or delete prompt sections.
- Do not reduce or expand contextual filtering.
- Do not redesign focus-chain generation.
- Do not redesign placeholder-workflow activation instructions.
- Do not redesign environment details.
- Do not redesign continuation-turn prompting.
- Do not migrate hook-context transport.
- Do not move human-authored input into the system prompt.
- Do not alter workspace-metadata transport for subagents.

## Verification Requirements

Implementation is not complete unless verification proves both transport cleanup and behavior preservation.

### Request-shape verification

Verification must prove that in-scope runtime-generated prompt content no longer rides in request `input`/conversation where it previously did.

This must include:

- main-task Responses-backed requests
- main-task non-Responses requests where applicable transport inspection is possible
- subagent requests
- OCA Responses requests

### Behavioral parity verification

Verification must prove that relocated blocks still appear with the same timing/configuration as before.

Minimum cases:

1. Main-task first turn with environment details and focus-chain guidance
2. Main-task continuation turn with current behavior preserved
3. Main-task continuation turn where the focus-chain checklist still appears in instructions after relocation
4. Main-task continuation turn where the auto-completed workflow-step notice still appears in instructions after relocation when present today
5. Main-task continuation turn where placeholder-workflow current-step guidance still appears in instructions after relocation
6. Deterministic placeholder workflow behavior unchanged
7. Compact/summarize-task path unchanged except for transport location
8. Responses-backed subagent continuation turn behavior unchanged
9. Non-Responses subagent behavior preserved except for transport relocation
10. OCA Responses request shape corrected

### Negative verification

Verification must also prove that excluded content remains excluded from relocation.

At minimum:

- subagent workspace metadata still appears only in the initial subagent user message
- hook-context transport remains unchanged

## Acceptance Criteria

This update is acceptable only if all of the following are true:

1. In-scope runtime-generated prompt content no longer travels as synthetic user/input prompt text.
2. That content instead travels through the request instructions/system-prompt path.
3. All existing contextual filters still behave exactly as they do now.
4. All full-prompt, refresh, first-turn, and continuation-turn behaviors remain unchanged.
5. Deterministic placeholder-workflow behavior remains unchanged.
6. The subagent workspace metadata block remains unchanged and stays in the initial user message.
7. OCA Responses no longer serializes the system prompt as a `role: "system"` input item.
8. No prompt wording changes are introduced.
9. No human-authored content is reclassified as system prompt content.

## Summary

The required change is transport normalization, not prompt redesign.

Move in-scope runtime-generated prompting from request input/conversation transport into request instructions/system-prompt transport.

Preserve:

- all existing prompt text
- all existing contextual gating
- all existing turn timing
- all existing provider/runtime behavior

Exclude only the subagent workspace metadata block and hook-context transport from this remediation.
