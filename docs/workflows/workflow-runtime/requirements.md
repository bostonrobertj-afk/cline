# Workflow Runtime Requirements

## 1. Introduction

### 1.1 Purpose

This document defines the software requirements for the workflow runtime initiative described in [project-overview.md](/Users/robertboston/Documents/Cline%20Extension/cline/docs/workflows/workflow-runtime/project-overview.md) and [architecture.md](/Users/robertboston/Documents/Cline%20Extension/cline/docs/workflows/workflow-runtime/architecture.md).

The goal of this project is to replace the current placeholder-workflow and BMAD-document-dependent workflow model with a product-owned workflow runtime that can orchestrate the approved in-scope workflows across turns, project workflow state into downstream capabilities, and safely support progression, completion, teardown, persistence, resume, and subagent-local workflow execution.

### 1.2 Document Conventions

- `must` indicates a mandatory requirement.
- `should` indicates a recommended requirement that may admit narrow exceptions only if explicitly approved by the user.
- `may` indicates an optional capability or future-facing allowance.
- Runtime identifiers, file paths, and code-owned concepts are written in monospace, for example `activeWorkflowName` and `task/index.ts`.
- Functional requirements are identified as `FR-x`.
- External interface requirements are identified as `IR-x`.
- Non-functional requirements are identified as `NFR-x`.

### 1.3 Intended Audience

This document is intended for:

- product and technical decision-makers aligning the workflow runtime scope
- backend/runtime engineers implementing the workflow runtime and workflow modules
- prompt and tool-surface owners integrating workflow-owned prompt and native tool schema
- UI/webview engineers maintaining focus chain and workflow form surfaces
- testers validating workflow activation, orchestration, progression, resume, and teardown behavior

### 1.4 Scope

The workflow runtime project supports the broader business and product goal of making the approved in-scope workflows reliable, maintainable, and scalable inside the extension backend.

The intended business and product benefits are:

- reduce architectural fragmentation caused by placeholder workflows, BMAD support files, and scattered workflow logic
- enable the approved in-scope workflows without recreating bespoke runtime seams
- improve correctness by giving workflow identity, active step, progression, completion, and resume one canonical runtime owner
- preserve existing specialist capabilities while moving workflow-specific orchestration into a cohesive runtime layer

## 2. General Description

### 2.1 Product Perspective

This product slice is an internal architectural replacement for the current workflow execution model inside the extension backend.

The current system evolved through multiple layers:

- placeholder workflow markdown and workflow placeholders
- BMAD support documents and persona/config assets
- focus chain ownership of active workflow step
- contextual workflow prompting scattered across task runtime and prompt components
- contextual tool gating and per-workflow bespoke seams
- workflow-form payload resolvers and workflow-specific deterministic execution helpers

The workflow runtime project replaces those fragmented ownership patterns with:

- one shared workflow runtime/orchestrator
- one code-owned workflow definition module per in-scope workflow
- one canonical workflow identity flag, `activeWorkflowName`
- runtime-owned workflow session state, active-step state, progression, completion, and resume
- runtime-owned workflow value ownership, mutation, and teardown semantics

### 2.2 Product Features

At a high level, the software must provide:

- workflow activation when an in-scope workflow is invoked through slash command or `useSkill`
- runtime-owned workflow session creation, mutation, persistence, resume, completion, and teardown
- runtime-owned workflow value persistence for values discovered during execution
- runtime-owned active-step resolution and progression
- workflow-module-defined prompt content and structured workflow definitions for native tool schema, transitions, deterministic resolution, workflow-form definitions, workflow-entry informational-panel content, and document-generation definitions/data, with the shared workflow runtime consuming those definitions and invoking the appropriate specialist capabilities
- projection of workflow state into downstream capabilities such as system prompt assembly, focus chain, and workflow forms
- support for concurrent parent and child workflow sessions using the same shared runtime implementation
- support for explicit parent-to-child workflow-value initialization where a child workflow definition declares it

### 2.3 User Classes and Characteristics

The relevant user classes are:

- end users invoking in-scope workflows through extension entrypoints
- primary AI agent runtime operating under an active workflow
- subagents explicitly assigned workflows through `useSkill`
- developers authoring and maintaining workflow modules and runtime orchestration
- testers validating workflow behavior across normal turns, deterministic paths, resume, and teardown

These users require predictable workflow identity, clear step ownership, safe resume behavior, and consistent downstream UI and prompt behavior.

### 2.4 Operating Environment

The workflow runtime must operate inside the existing extension backend/runtime process and interoperate with:

- `task/index.ts` as the application-level orchestrator
- the system prompt architecture as the final prompt assembler
- the existing workflow form surface
- focus chain as a workflow-only downstream projection surface
- the normal tool execution path
- local persistence used by task/runtime state
- parent and child execution contexts used for main-agent and subagent operation

### 2.5 Constraints

The following constraints apply:

- `task/index.ts` remains the application-level orchestration entrypoint.
- `activeWorkflowName` is the sole canonical workflow-identity flag.
- `activeWorkflowName` must not become the carrier for session state, active-step state, or other per-turn workflow state.
- The system prompt architecture remains responsible for final prompt assembly.
- Existing specialist capabilities such as workflow forms and normal tool execution remain specialist capabilities rather than being absorbed wholesale into the runtime.
- User-authored workflows are out of scope for the target architecture.
- Any shipped workflow outside the approved in-scope workflow set is out of scope for this initiative.
- Managed workflows are being retired.
- Placeholder workflow markdown and workflow placeholders are being retired as canonical workflow owners.
- Workflow-owned values discovered during execution must continue to have one canonical runtime-owned persistence surface after placeholder workflows are retired.
- `task_progress` is being retired, and focus chain is becoming a workflow-only surface.
- Full implementation will be carried out through a series of tightly-scoped action plans:
  - Foundational Build
  - Module Builds (one per workflow being implemented in the new architecture)
  - Cleanup
- Temporary bridges and compatibility patches intended to maintain compile-time functionality are not required or permitted- the app will be offline for the duration of the build.
- Any legacy surface the migration matrix marks `Delete` must be removed from the live runtime dependency chain during the phase that replaces its behavior; if physical file deletion is deferred, that surface must still be fully decoupled and dead code before cleanup.
- Action plan authors must identify all files which must be modified during the action plan, then identify all necessary code revisions within the action plan's scope per file, then ensure that tasks/ subtasks are organized by file to avoid having developers touch the same file multiple times and/or revise code that was put in place during the same action plan.
- the ".md" convention must not be included in workflow names in the new architecture.

### 2.5a Implementation Phase Model

This initiative is structured into three implementation phases plus global requirements that constrain all phases:

- `Global`: Architecture constraints, canonical ownership rules, and end-state invariants that must be respected by every action plan regardless of phase.
- `Foundational Build`: Shared runtime, shared prompt/tool architecture, shared workflow contracts, shared deterministic/document-generation infrastructure, and non-module-specific migrations that must exist before workflow-specific module buildout can proceed safely.
- `Module Builds`: One action plan per workflow, limited to that workflow's module-defined prompting, transitions, workflow forms, workflow-entry informational-panel content, deterministic rules, document-builder definitions, templates/builders, and workflow-specific migrations explicitly tied to that workflow.
- `Foundational Build` and `Module Builds` must decouple any migration-matrix `Delete` surfaces they replace from the live runtime so those surfaces are dead code before the `Cleanup` phase physically removes them.
- `Cleanup`: Deletion of legacy files, helpers, registries, prompt seams, and reference-only assets after the required foundational and module-build replacements are in place.

Unless a requirement or matrix row note states otherwise, the phase labels in Section 3 indicate the primary phase in which that requirement must be satisfied. Sections 4 and 5 remain global unless a requirement there explicitly states otherwise.

### 2.6 Assumptions and Dependencies

This requirements set assumes:

- the approved in-scope workflows will be registered in product-owned runtime code
- workflow-specific prompt content can be owned by workflow modules and consumed by the system prompt architecture
- workflow-specific native tool schema can be owned by workflow modules and consumed during system prompt assembly for the active step
- a persistence mechanism remains available for storing the minimum workflow session state required for safe resume
- the existing workflow form surface and focus chain remain available as downstream renderers
- subagent workflows are explicitly assigned and activated in child execution contexts only
- some child workflows may need selected workflow values copied from parent workflow state during activation

This project depends on:

- `task/index.ts` integration for activation and runtime invocation
- prompt architecture integration for workflow prompt data and workflow-owned native tool schema
- focus chain integration for runtime-projected workflow step/status display
- workflow form integration for rendering workflow-owned payloads
- shared mandatory entry workflow-form UI integration for collecting the pre-workflow informational and project-selection inputs required by `FR-10d` through `FR-10l`
- normal tool execution for deterministic operations

## 3. System Requirements

### 3.1 Functional Requirements by Implementation Phase

The functional requirements below are grouped by the primary implementation phase in which they must be considered. Global requirements constrain all phases. Foundational Build requirements establish shared architecture and shared runtime seams. Module Build requirements define workflow-specific module work. Cleanup requirements govern retirement of legacy workflow surfaces once the required replacements are in place.

#### Global Requirements: Activation and Identity

- `FR-1`: The system must detect in-scope workflow invocation through slash command and `useSkill` entrypoints in `task/index.ts`.
- `FR-2`: The system must set `activeWorkflowName` when a workflow is activated.
- `FR-3`: `activeWorkflowName` must be the canonical answer to whether a workflow is active and which workflow is active.
- `FR-4`: The system must retire parallel workflow-identity carriers used by the current runtime, including placeholder-workflow identity fields and managed-workflow identity state.
- `FR-5`: `WorkflowRuntime` must resolve the active workflow definition from the product-owned registry of in-scope workflows for this initiative, using `activeWorkflowName` as the canonical workflow identity, rather than relying on user-authored workflow discovery.
- `FR-5a`: The system must support explicit `useSkill` activation of in-scope shipped workflows by resolving the requested skill name through the shipped workflow-definition registry when `use_skill` is otherwise available to the model or is exposed by an active workflow module; shipped workflows must not force default non-workflow `use_skill` exposure and must not be automatically listed in the main-agent or subagent prompt `SKILLS` discovery surface.
- `FR-5b`: The canonical seam for shipped-workflow `useSkill` activation lookup must be `resolveWorkflowByUseSkillName(...)`.
- `FR-5c`: `resolveWorkflowByUseSkillName(...)` must resolve shipped workflows from runtime workflow definitions and their workflow-module-owned `useSkillName` identity fields, rather than from legacy resolved-workflow entry shapes or prompt-visible `SkillMetadata` projection.
- `FR-5d`: Local, global, remote, and managed workflow-source discovery must not participate in shipped-workflow `useSkill` activation lookup.
- `FR-5e`: The legacy helper `createWorkflowSkillMetadata(...)` must be retired with no replacement prompt-visible workflow skill metadata projection.
- `FR-5f`: Main-agent `useSkill` execution paths must resolve shipped workflow names through the product-owned workflow registry lookup whenever `use_skill` is invoked, without injecting shipped workflow metadata into prompt-visible skill discovery by default and without requiring default non-workflow `use_skill` tool exposure when no ordinary skills are available.
- `FR-5g`: Subagents must not directly execute `use_skill`. A child workflow session may be activated only by parent-assigned subagent workflow configuration, and that assigned workflow activation must resolve shipped workflow names through the product-owned workflow registry lookup.
- `FR-5h`: Every successful workflow activation path must pass the `WorkflowNextAction` returned by `WorkflowRuntime.activateWorkflow(...)` into the canonical next-action consumer in the same execution context before workflow execution continues. This applies to slash-command activation, main-agent `use_skill` workflow activation, and parent-assigned child workflow activation.
- `FR-5i`: A tool-based workflow activation path may emit its normal tool result first, but it must preserve the activation next action and hand it to the canonical next-action consumer immediately after the tool result is recorded. Tool handlers must not drop the activation result, consume it privately, or substitute ad hoc re-resolution logic.

#### Foundational Build Requirements: Workflow Runtime Ownership

- `FR-6`: The system must introduce a shared workflow runtime that is invoked by `task/index.ts` whenever a workflow is active.
- `FR-7`: The workflow runtime must create and own workflow session state for each execution context in which a workflow is active.
- `FR-8`: The workflow runtime must own active-step state.
- `FR-9`: The workflow runtime must own progression evaluation, advancement, completion detection, teardown, persistence, and resume for active workflow sessions.
- `FR-10`: The workflow runtime must define and enforce canonical workflow session mutation rules.
- `FR-10a`: The workflow runtime must define and enforce one canonical mutation surface for workflow-owned values.
- `FR-10b`: Backend-owned deterministic logic and AI-callable workflow-value persistence must both write to the same canonical workflow value carrier inside workflow session state.
- `FR-10c`: The canonical carrier for workflow-owned values must live inside workflow session state rather than in separate mirrored task-state fields.
- `FR-10c1`: Each workflow module must declare the canonical inventory of workflow-value keys supported by that workflow; `WorkflowRuntime.applyWorkflowValueWrites(...)` must reject or no-op any write for a key not present in the active workflow definition's inventory.
- `FR-10d`: For user-facing main-agent workflow invocations, the workflow runtime must run one mandatory shared pre-workflow entry `WorkflowForm` before workflow-specific step orchestration begins.
- `FR-10d1`: The mandatory shared pre-workflow entry `WorkflowForm` must run for every user-facing main-agent workflow invocation in the target architecture.
- `FR-10d2`: Child/subagent workflow activation must not render the mandatory shared pre-workflow entry `WorkflowForm`; child workflow sessions must initialize project identity by copying the parent workflow session's project selection during activation, and activation must no-op if that parent project selection is unavailable or incomplete.
- `FR-10d3`: Child/subagent workflow sessions must not render workflow forms, including mandatory entry forms and active-step workflow forms. If next-action evaluation for a child workflow returns a workflow-form render action, the runtime must fail clearly as invalid child workflow configuration rather than silently no-op or render UI.
- `FR-10e`: The first panel of that mandatory shared pre-workflow entry `WorkflowForm` must be informational only and must carry the workflow-specific informational content that legacy workflow start cards used to carry.
- `FR-10f`: The second panel of that mandatory shared pre-workflow entry `WorkflowForm` must obtain or resolve project identity for the active workflow session by presenting a `new` versus `existing` project choice.
- `FR-10g`: If `existing` is chosen, the system must derive the available project choices by calling `fs.readdir(<visible project output root>, { withFileTypes: true })`, filtering to immediate child directory `Dirent`s only, and mapping each surviving folder basename to a project choice.
- `FR-10g0`: For the foundational runtime, `<visible project output root>` is the `cwd` supplied to `WorkflowRuntime` by the active `Task`; existing-project discovery, new-project folder creation, and workflow artifact destination resolution must treat that `cwd` as the project-output root.
- `FR-10g1`: The second panel of the mandatory shared pre-workflow entry `WorkflowForm` must treat that `fs.readdir(..., { withFileTypes: true })` plus `Dirent` filtering flow as its canonical filesystem-discovery method rather than glob-driven discovery, hidden registries, or workflow-specific discovery tooling.
- `FR-10g2`: The second panel of the mandatory shared pre-workflow entry `WorkflowForm` must consume the same shared runtime-owned discovery/list-builder seam used by workflow-form selection flows so existing-project selection and in-workflow existing-artifact selection follow one canonical methodology.
- `FR-10h`: If `new` is chosen, the system must collect a user-provided project title.
- `FR-10i`: The workflow runtime must normalize user-provided project titles into filesystem-safe project identity.
- `FR-10j`: The workflow runtime must preserve the user-provided project title as human-facing project text while using the normalized filesystem-safe identity for folder creation and path resolution.
- `FR-10k`: The workflow runtime must ensure the per-project folder exists before workflow-specific artifact-producing steps can run.
- `FR-10l`: The workflow runtime must ensure these canonical project subfolders exist within each per-project folder before workflow-specific artifact-producing steps can run:
  - `discovery`
  - `planning`
  - `implementation`
  - `review`
  - `testing`

#### Module Build Requirements: Workflow Modules

- `FR-11`: Each in-scope workflow must be represented by a code-owned workflow module.
- `FR-12`: Each workflow module must define workflow identity and metadata.
- `FR-12a`: Each workflow module must define the canonical project subfolder designation for that workflow.
- `FR-13`: Each workflow module must define its step graph and transition rules.
- `FR-14`: Each workflow module must define workflow-level and per-step prompt content.
- `FR-14a`: Workflow-module prompt content must be implemented as code-owned prompt-builder functions that accept explicit typed runtime inputs and return fully assembled prompt strings for the active workflow or step.
- `FR-14b`: The workflow runtime must resolve the runtime-owned workflow/session values required for the active prompt before invoking the workflow module's prompt-builder function.
- `FR-14c`: The system must not treat workflow prompt content as placeholder-tokenized text resolved through a generic placeholder subsystem, placeholder workflow markdown, managed-workflow placeholder state, `.cline/workflow-config.yaml`, or similar placeholder-era resolution helpers.
- `FR-14d`: Existing string-formatting utilities may be used inside workflow-module prompt-builder functions only as local formatting helpers with explicitly provided inputs. They must not serve as a generic workflow-placeholder contract.
- `FR-14e`: The output of a workflow-module prompt-builder function must be a fully assembled prompt string ready for system-prompt inclusion. Unresolved placeholder markers must not remain part of the workflow prompt contract.
- `FR-14f`: Workflow prompt projection is step-bound. Workflow-module prompt-builder functions may vary prompt content by active workflow, active step, and explicit runtime/session values passed into the prompt-builder input, but must not depend on the identity of the next-action decision route or rule that selected model-driven continuation.
- `FR-14g`: If a workflow needs materially different model instructions after a next-action decision, the workflow module must represent that difference by transitioning to a different step or by persisting an explicit workflow/session value that the active step prompt builder reads. A next-action route that hands control back to model-driven work must not expect route-specific prompt text to be carried by the next-action result itself.
- `FR-15`: Each workflow module must define workflow-level defaults and per-step native tool schema for model exposure.
- `FR-16`: Each workflow module must define a per-step next-action decision tree that expresses workflow progression and other runtime-owned branch behavior. That decision tree must let the module declare branch triggers, following branch targets, and any explicit step-transition target reached by a satisfied branch. Supported branch triggers must be workflow-module-declared, runtime-observable outcomes and state conditions, including but not limited to deterministic success, deterministic failure, `workflow_progress_request` confirm, `workflow_progress_request` deny, workflow-form or other UI selections, workflow-value persistence or resolution, artifact/file creation or update, document/content-state assertions, and final report delivery outcomes.
- `FR-16a`: Deterministic workflow behavior is not synonymous with tool execution. Runtime-owned deterministic procedures include workflow-state evaluation, filesystem discovery/list building, workflow-form option population, workflow-value persistence, artifact identity/path derivation, completion detection, teardown, and next-action re-evaluation.
- `FR-16b`: Runtime-owned deterministic procedures must execute inside `WorkflowRuntime` or shared runtime-owned seams, not be modeled as tool calls solely to fit the next-action engine.
- `FR-16c`: Tool-backed deterministic operations are the subset of deterministic behavior that must use the normal tool execution path because they perform tool-governed work such as file creation/update/delete, document generation, artifact creation, subagent dispatch, or other actions subject to existing tool approval, policy, or execution controls.
- `FR-16e`: Any workflow-supporting tool, runtime-invoked capability, or tool-backed deterministic operation that reads, writes, creates, updates, deletes, or otherwise accesses workspace files must use the existing workspace path-policy seam before touching disk. User approval, auto-approval, and tool hooks must not bypass, replace, or run before that path-policy check.
- `FR-16f`: `WorkflowRuntime` must receive the same initialized workspace path-policy seam used by normal tool execution from the parent `Task` execution context; it must not instantiate an independent path-policy controller.
- `FR-16g`: Runtime-owned discovery/list-building must validate the target directory through the workspace path-policy seam before `readdir`; denied target paths must fail explicitly rather than returning empty discovery results.
- `FR-16h`: Runtime-owned discovery/list-building must filter discovered child entries through the workspace path-policy seam before returning candidates to workflow forms, artifact allocation, prompts, or tool payloads.
- `FR-16i`: Runtime-owned file and directory creation must validate every concrete path through the workspace path-policy seam before `mkdir` or `writeFile`, including entry project root folders, canonical project subfolders, artifact parent directories, and artifact file paths.
- `FR-16j`: Handler-level path-policy validation does not satisfy runtime-owned filesystem access. When a tool delegates to `WorkflowRuntime`, both the handler boundary and runtime-owned filesystem access must enforce path policy at their own boundary.
- `FR-16k`: Any legacy workflow file-accessing capability that is re-established during a workflow module build, including code-review spec/review-input updates, story-task file updates, or workflow-specific document/artifact writers, must satisfy `FR-16e` through `FR-16j` before disk access. Module-build implementations must not preserve or reintroduce direct legacy `fs` reads/writes that bypass the existing workspace path-policy seam.
- `FR-16d`: A single next-action evaluation may perform runtime-owned deterministic procedures needed to evaluate state, then select at most one externally visible next action or one tool-backed deterministic operation.
- `FR-17`: Each workflow module must define workflow form configuration where applicable.
- `FR-17a`: Workflow modules must not define or preserve a standalone workflow-start-card capability or standalone workflow-start form configuration. Any workflow-specific entry content that legacy workflow start cards used to carry must instead be supplied as the informational first panel of the shared pre-workflow entry `WorkflowForm`.
- `FR-18`: Each workflow module must define deterministic step-resolution rules where deterministic resolution is supported.
- `FR-19`: `WorkflowRuntime` must determine workflow completion by whether the active workflow has reached and completed its final step, and on completion must execute workflow-agnostic teardown.
- `FR-20`: Each workflow module must define any workflow-owned document or artifact builder definitions needed to produce workflow outputs.
- `FR-20a`: The workflow runtime must use the workflow's canonical project subfolder designation when resolving that workflow's artifact destinations inside the selected project folder.
- `FR-20b`: `WorkflowRuntime` must own the shared hierarchical artifact identity and numbering policy used to connect related workflow outputs inside a project.
- `FR-20b1`: Canonical numbered artifact identities must use dotted numeric form in runtime/session/user-facing identity: epic `1`, story `1.1`, remediation story `1.1.1`.
- `FR-20b1a`: Canonical singleton project artifact identities must use stable registry-owned string identities rather than dotted numeric identities. `Epics.md` must use `epics`; `Epics.index.json` must use `epics_index`.
- `FR-20b1b`: `FR-20b1` and `FR-20b1a` define the canonical normalized artifact identities after runtime resolution. At artifact parent or target identity input boundaries, `WorkflowRuntime` may accept artifact identity input values in canonical dotted form, canonical singleton identity form, canonical filename form from `FR-20b2`, or the hyphenated numeric target fragment used inside those filenames.
- `FR-20b1c`: Accepted artifact identity input aliases must be normalized by `WorkflowRuntime` to canonical dotted or singleton form before artifact validation, artifact derivation, filename construction, path construction, and runtime-owned artifact output persistence. Accepted input aliases do not create additional canonical identity models.
- `FR-20b1d`: Artifact identity input normalization is runtime-owned. Workflow modules must not parse artifact filenames, replace separators, derive lineage segments, or compute parent or target artifact identities themselves.
- `FR-20b2`: Filesystem-safe artifact filename forms must use these canonical filename patterns: `Epics.md`, `Epics.index.json`, `Epic-{E}-delivery-spec.md`, `Story-{E}-{S}.md`, `Remediation-story-{E}-{S}-{R}.md`, `Review-blind-hunter-{target}.md`, `Review-edge-case-hunter-{target}.md`, `Adversarial-review-{target}.md`, `Review-input-{target}.md`, and `Review-input-{target}.diff`, where `{E}` is the selected epic number, `{S}` is the story number within that epic, `{R}` is the remediation-story number within that story, and `{target}` is the hyphenated identity of the selected story or remediation-story target.
- `FR-20b2a`: `Epics.md` is the project-level, human-facing epics artifact. It is unnumbered and contains all high-level epics for the project.
- `FR-20b2b`: `Epics.index.json` is the project-level, machine-readable epic inventory artifact. The workflow that creates or updates `Epics.md` must also create or update `Epics.index.json`.
- `FR-20b2c`: `Epics.index.json` must contain the structured epic identities needed by runtime/module logic to select or validate an epic without parsing markdown content from `Epics.md`.
- `FR-20b2c1`: `Epics.index.json` must use this schema: `{ "version": 1, "epics": [{ "identity": "1", "title": "..." }] }`. `identity` must be a positive numeric string, `title` must be a non-empty string, and the index must not contain story, remediation-story, or review data.
- `FR-20b2d`: Epic-delivery-spec artifacts are unique per epic, inherit the selected epic identity exactly from the structured epic inventory, and must not allocate a separate delivery-spec-specific number.
- `FR-20b3`: Runtime must derive a new `Epic-{E}-delivery-spec.md` identity by reading `Epics.index.json`, sorting indexed epic identities numerically, discovering existing convention-matching `Epic-{E}-delivery-spec.md` files, and selecting the first indexed epic identity without a matching delivery spec. Runtime must not parse `Epics.md` markdown content or treat `Epic-{E}.md` files as canonical.
- `FR-20b4`: Runtime must allocate story numbers within the selected parent epic.
- `FR-20b4a`: Story allocation must validate the selected parent epic identity against an existing convention-matching `Epic-{E}-delivery-spec.md`; `Epics.index.json` alone is not sufficient proof that story artifacts may be allocated for that epic.
- `FR-20b5`: Runtime must allocate remediation-story numbers within the selected parent story.
- `FR-20b6`: QA/review artifacts must inherit the selected target story or remediation-story identity exactly, must use that inherited identity in the canonical filename, and must not allocate or increment any review-specific number.
- `FR-20b6a`: Review artifact creation must fail through the runtime tool-backed operation result path when no convention-matching `Story-{E}-{S}.md` or `Remediation-story-{E}-{S}-{R}.md` target artifact is selected.
- `FR-20b7`: Workflow modules may declare artifact family, parent/target requirements, and artifact type, but must not compute, increment, parse, or format canonical artifact numbers themselves.
- `FR-20b8`: Runtime numbering must be based on convention-driven filesystem discovery, not a hidden artifact registry.
- `FR-20b9`: Runtime artifact creation must not use collision suffixing as canonical artifact numbering. Runtime must use convention-driven filesystem discovery before write to avoid known canonical filename collisions, and must create new artifacts with exclusive-write semantics so existing files are never overwritten.
- `FR-20b9a`: Unexpected write-time `EEXIST` collisions after runtime discovery are accepted as a low-likelihood race/staleness risk for the foundational build. When such a collision occurs, runtime may fail clearly rather than suffixing, overwriting, or treating the existing file as the newly allocated artifact.
- `FR-20c`: The shared numbering policy must carry forward across epics, epic-delivery-spec, story, remediation-story, and QA/review artifact families, including both human-facing artifacts and machine-readable sidecar/index artifacts where required by a family.
- `FR-20d`: The architecture must provide one shared deterministic document-generation tool in the existing tool runtime layer rather than separate workflow-specific document-generation tools.
- `FR-20e`: When a workflow needs to create or update a workflow-owned text artifact, the workflow runtime must invoke that shared document-generation tool through the normal tool execution path.
- `FR-20f`: The workflow runtime must derive shared document-generation tool inputs from the active workflow module and runtime-owned workflow state. Workflow modules may provide template/builder selection, formatting rules, and source content inputs, but runtime-owned artifact allocation must provide canonical output identity, filename, project-relative path, and absolute destination path.
- `FR-20g`: Workflow modules must express document-builder definitions using one consistent methodology and one consistent typed structure across all workflow modules so the workflow runtime can resolve document-generation inputs with the same code path regardless of which workflow is active.
- `FR-20h`: Workflow modules must not require workflow-specific bespoke document-generation handlers in the tool runtime for workflow-owned text artifact creation or update.

- `FR-20i2`: `create_workflow_artifact` must be invokable by `WorkflowRuntime` deterministic next-action evaluation when a workflow module declares artifact creation or derivation.
- `FR-20i3`: `create_workflow_artifact` must also be callable by the AI agent when, and only when, the active workflow module includes it in that turn's complete runtime-projected workflow tool schema.
- `FR-20i4`: `create_workflow_artifact` must not have static default/global prompt or native-tool exposure.

- `FR-20i7`: Because `create_workflow_artifact` creates a file, it must satisfy `FR-16e` and must also use the existing file-write approval, auto-approval, and hook seams before file creation.

- `FR-20j2`: Before allocating a dependent artifact, runtime must normalize the declared parent or target identity input, validate that the normalized identity resolves to a convention-matching artifact in the selected project, and route failure through the runtime tool-backed operation result path.

- `FR-20j3a`: The artifact-family registry must explicitly model singleton project artifacts, epic-index-derived artifacts, newly numbered artifacts, and target-derived artifacts as separate allocation or derivation modes.
- `FR-20j4`: Workflow modules may reference runtime-owned artifact-family identifiers from that registry, but must not define or override canonical artifact-family filename patterns, extensions, numbering scopes, or discovery patterns.
- `FR-20j5`: When an artifact family requires a structured sidecar/index artifact for identity selection or validation, that sidecar/index behavior must be represented in the runtime-owned artifact-family registry rather than implemented as module-specific filename or markdown-parsing logic.
- `FR-20k`: Workflow modules must not prescribe canonical artifact filenames, increment artifact numbers, or compute canonical artifact paths.
- `FR-20l`: The artifact allocation/create capability must resolve the active project, allocate or derive the canonical artifact identity, produce the canonical filename, project-relative path, and absolute path, and persist those outputs into workflow session values.
- `FR-20m`: Persisted artifact outputs must include project context sufficient for prompt and tool clarity, including project title, project filesystem identity or folder, artifact family, artifact identity, artifact filename, artifact relative path, artifact absolute path, and parent or target identity when applicable.
- `FR-20n`: The artifact allocation/create capability must create the empty artifact file at the resolved canonical path before reporting success.
- `FR-20o`: Artifact allocation/create failures must be represented as runtime tool-backed operation results and re-enter canonical next-action evaluation rather than being handled by module-specific ad hoc logic.
- `FR-20p`: The shared `build_workflow_document` capability must remain a content writer only; it must consume a runtime-resolved destination path and must not allocate artifact identity, compute canonical filenames, or choose project folders.

#### Foundational Build Requirements: Step Resolution and Progression

- `FR-22`: The workflow runtime must resolve the current active step from workflow session state rather than from focus chain markdown or checklist state.
- `FR-23`: Focus chain must no longer act as the canonical owner of active workflow step.
- `FR-24`: The system must treat focus chain as a downstream consumer that reflects runtime-owned workflow step and status.
- `FR-24a`: Focus-chain lifecycle must be workflow-scoped, not task-global.
- `FR-24b`: Task execution must not instantiate `FocusChainManager` from global focus-chain settings when no runtime workflow session is active.
- `FR-24c`: When no runtime workflow session is active, task execution must not route through focus-chain refresh, prompt-instruction, checklist-update, or completion-protection paths.
- `FR-24d`: Child/subagent execution contexts must not instantiate or use `FocusChainManager`; child workflow prompt projection must come from `WorkflowRuntime.buildTurnProjection(...)`, and child workflow state must remain in the child runtime workflow session.
- `FR-25`: The system must support model-driven progression requests through `workflow_progress_request` only when the workflow runtime indicates that mechanism is permitted for the active step.
- `FR-26`: A user approval returned through the `workflow_progress_request` flow must not progress a workflow directly; it must be handed to the workflow runtime for validation and canonical state mutation.
- `FR-27`: The system must retire `task_progress` as a workflow progression mechanism.
- `FR-28`: The system must retire direct AI tools whose purpose is to progress focus chain independently of workflow runtime state.
- `FR-29`: The workflow runtime must evaluate the active workflow state and determine the canonical next action for the current turn.
- `FR-29a`: The canonical next-action evaluation must be a unified runtime-owned capability rather than separate subsystem-specific trigger mechanisms.
- `FR-29b`: Workflow modules must define the tree-structured branch rules, branch conditions, and following branch targets that inform next-action evaluation for their workflows. `WorkflowRuntime` must evaluate that module-owned decision tree from the active branch context and runtime state rather than treating next-action rules as an unstructured first-match ordered array.
- `FR-29b1`: Workflow step ids must use the canonical `step-{stepNumber}` form and must exactly match the step's numeric `stepNumber`, for example `step-1` for `stepNumber: 1`.
- `FR-29b2`: Workflow decision-tree routes within the same branch must be configured so their trigger conditions are mutually exclusive for any single next-action evaluation. Route array order must not be treated as an intentional priority mechanism or workflow behavior contract.
- `FR-29b3`: Next-action decision-tree routes that hand control back to model-driven workflow execution must target active step/session state that can produce the required step-bound prompt projection under `FR-14f` through `FR-14g`.
- `FR-29c`: The canonical next action may include rendering the mandatory shared pre-workflow entry `WorkflowForm`, rendering an active-step workflow form, invoking a deterministic operation, allowing normal model-driven progression, emitting completion behavior, or taking no workflow-specific action.
- `FR-29c1`: Each canonical next-action evaluation must select at most one immediate runtime action.
- `FR-29c2`: If the selected immediate action is tool-backed, it must resolve to exactly one tool execution request. A single next-action rule or decision action must not bundle, fan out, or require multiple tool calls before result evaluation.
- `FR-29c3`: Workflows that require multiple tool-backed operations must model them as a sequence of next-action evaluations. Each tool result must be interpreted and applied to workflow session state before the decision tree is re-evaluated to select any later tool-backed operation.
- `FR-29c4`: Runtime next-action evaluation must distinguish dedicated runtime-owned operation actions from generic module-owned tool-backed operations. Runtime-owned capabilities with dedicated seams, including artifact allocation/create, workflow document building, workflow-value persistence, and workflow progress requests, must not be routed through generic module-owned tool-backed operation definitions.
- `FR-29c5`: Generic module-owned tool-backed operation definitions may be used only for one-tool deterministic work that does not already have a dedicated runtime-owned seam.
- `FR-29c6`: A next action that returns control to model-driven workflow execution is a prompt-projection handoff. The consumer must persist active workflow metadata before returning, and prompt content must come from normal step-bound projection under `FR-14f` through `FR-14g`, not from next-action-rule-specific prompt text.
- `FR-29d`: Workflow-form interruption logic must not remain a separate canonical trigger subsystem outside `WorkflowRuntime`.
- `FR-29e`: Deterministic step-resolution logic must not remain a separate canonical trigger subsystem outside `WorkflowRuntime`.
- `FR-29f`: Whenever `WorkflowRuntime` must identify existing projects, folders, files, or artifacts for the mandatory shared pre-workflow entry `WorkflowForm`, active-step workflow-form behavior, deterministic-step behavior, or other runtime-owned next-action evaluation, it must call one shared runtime-owned discovery/list-builder seam. That seam must use `fs.readdir(<target directory>, { withFileTypes: true })` plus `Dirent` filtering as its canonical enumeration primitive and must return a normalized candidate array for user selection or runtime evaluation.
- `FR-29f1`: The shared discovery/list-builder seam must accept typed discovery parameters, including target-directory resolution, entry-type filtering, immediate-child filtering, naming-convention matching, and deterministic sorting rules.
- `FR-29f2`: The shared discovery/list-builder seam must return normalized selection candidates that separate display text from canonical value so the same seam can support both project selection and workflow-specific artifact selection.
- `FR-29g`: Workflow modules may declare what must be discovered, which filters and naming conventions apply, how candidates should be labeled, how they should be sorted, and which workflow-value key should receive the selected canonical value, but they must not introduce workflow-specific filesystem-scanning tools or workflow-specific enumeration helpers.
- `FR-29h`: All `WorkflowNextAction` values returned by workflow activation, workflow-form submission, workflow-value persistence, workflow-progress request handling, tool-backed operation result handling, or explicit runtime next-action evaluation must be consumed by one canonical next-action consumer. Callers must not silently drop returned next actions or create path-specific mini-orchestrators.
- `FR-29i`: The canonical next-action consumer may be called through main-task and child/subagent context adapters, but branch/result interpretation remains owned by `WorkflowRuntime`.
- `FR-29j`: Workflow module decision trees may branch only on documented runtime decision inputs: the active branch id, the current step definition, workflow values declared in the active workflow's canonical workflow-value inventory, and documented `WorkflowBranchTriggerEvent` variants.
- `FR-29k`: Runtime-owned UI bookkeeping fields, including `suppressedWorkflowFormIds` and `suppressedWorkflowStepResolutionDefinitionIds`, are internal runtime state used to prevent repeated rendering/execution within the current step. Workflow modules must not depend on those fields in `session_predicate` or `event_predicate` route logic.
- `FR-29l`: `WorkflowBranchTriggerEvent` variants are part of the module-authoring contract only when the runtime explicitly emits them. The foundational runtime must not expose non-emitted trigger variants as valid module-visible branch events.
- `FR-29m`: `session_initialized` is not an approved module-visible branch event unless the runtime emits it during workflow activation and the event is documented as part of the workflow module contract. Until then, modules must use the step entry branch and `always` routes for initial step behavior.
- `FR-30`: The system must retire `WorkflowStepResolutionRegistry` as a separate canonical owner of workflow step-resolution behavior.

#### Foundational Build Requirements: Prompting and Native Tool Exposure

- `FR-31`: The workflow runtime must assemble exactly three workflow-owned per-turn prompt/tool outputs for the active turn: a workflow instructions block for system instructions, a workflow instructions block for input, and any workflow-specific native tool schema override.
- `FR-31a`: The workflow runtime must support both a full-turn variant and a continuation-turn variant for the system-instructions workflow block and for the input workflow block.
- `FR-31b`: No workflow-specific prompt content may be projected through any prompt carrier other than the runtime-owned workflow instructions block for system instructions and the runtime-owned workflow instructions block for input.
- `FR-32`: The system prompt architecture must remain the final assembler of the full system prompt.
- `FR-33`: Workflow modules must own the actual workflow-specific and step-specific prompt strings.
- `FR-33a`: Workflow modules are the sole source of workflow-specific and step-specific prompt content used to build the runtime-owned workflow instructions blocks.
- `FR-34`: For each turn, the workflow runtime must build the workflow instructions blocks from workflow-module prompting plus runtime-owned workflow/session state.
- `FR-34a`: The system-instructions workflow block must include the current workflow step list with `[x]` / `[ ]` indicators in both the full-turn and continuation-turn variants.
- `FR-34b`: The system-instructions workflow block must include a workflow persona section only when the workflow is active on the task's first API request, defined by `TaskState.apiRequestCount === 1`. Workflows are expected to be user-invoked in fresh task threads, so persona projection is task-first-turn gated rather than separately tracking a workflow-first-turn flag.
- `FR-34c`: The input workflow block full-turn variant must include a `Current Step` section containing the active step prompting from the workflow module.
- `FR-34d`: The input workflow block continuation-turn variant must omit the `Current Step` section.
- `FR-35`: The workflow runtime must project the complete workflow-owned native tool schema that applies on the current turn from the active workflow module.
- `FR-35a`: `set_workflow_values` is the canonical workflow-value persistence tool name/capability only when a workflow module exposes workflow-value writes for the active turn.
- `FR-35b`: `set_workflow_values` must not have a static shared fallback prompt/native schema.
- `FR-35c`: The model may see `set_workflow_values` only when the active workflow module includes it in that turn's complete module-derived tool schema.
- `FR-35d`: Workflow modules own the schema shape for any exposed `set_workflow_values` entry.
- `FR-35e`: A module-provided `set_workflow_values` schema must expose only workflow-value keys from the workflow's canonical workflow-value inventory and only the subset the workflow module chooses to make AI-writable for the active step.
- `FR-35e1`: When the active workflow module includes `set_workflow_values` in the current step schema, that schema is the authoritative module-owned definition of which inventory keys are model-visible for that turn.
- `FR-35e2`: Module-owned native tool schema correctness is a module-build responsibility. Foundational runtime projection must consume the complete tool schema returned by the active workflow step and must not rewrite, filter, or validate arbitrary module-owned native tool schema contents during turn projection.
- `FR-35f`: If the active workflow module does not include `set_workflow_values` in the current turn's complete tool schema, the system prompt architecture must not expose `set_workflow_values` for that turn.
- `FR-35g`: Regardless of the module-provided schema shown to the model, execution of `set_workflow_values` must write through the canonical workflow-runtime workflow-value mutation seam into the active workflow session only.
- `FR-35g1`: `WorkflowRuntime.applyWorkflowValueWrites(...)` must validate every requested workflow-value key against the active workflow definition's canonical workflow-value inventory before persisting it.
- `FR-35g2`: Runtime persistence authorization is based on the active workflow definition's canonical workflow-value inventory; the active step's `set_workflow_values` schema controls model-visible exposure for that turn, not the runtime persistence allowlist.
- `FR-35h`: `set_workflow_values` must not read from or write to placeholder-era workflow state, managed-workflow state, `.cline/workflow-config.yaml`, or similar legacy workflow surfaces.
- `FR-35i`: The canonical workflow-value carrier must support JSON-safe values: strings, numbers, booleans, arrays whose entries are workflow values, and object maps whose property values are workflow values.
- `FR-35j`: `WorkflowRuntime.applyWorkflowValueWrites(...)` must preserve workflow-value type and shape. It must not stringify arrays or objects for storage and must not silently drop supported JSON-safe values.
- `FR-35k`: Runtime workflow-value comparison must use deterministic value equality for JSON-safe values rather than string-only comparison.
- `FR-35l`: Workflow prompt builders may insert workflow values into instruction text only through deterministic rendering: strings as-is, numbers and booleans through `String(value)`, and arrays and objects as stable JSON.
- `FR-35m`: Runtime or tool code that requires a string workflow value, including artifact identity, artifact path, file path, or folder resolution, must explicitly validate that the stored value is a non-empty string before use and fail with a clear runtime error otherwise.
- `FR-36`: The system prompt architecture must assemble exactly one workflow instructions section in system instructions and exactly one workflow instructions section in input by consuming the runtime-owned full-turn or continuation-turn workflow blocks for the current turn, and must consume any runtime-projected workflow-specific native tool schema override for that turn.
- `FR-37`: The architecture must retire workflow-specific reliance on contextual tool gating as the canonical owner of workflow tool exposure behavior.
- `FR-38`: Workflow reminder behavior from the current system must be retired or migrated into the workflow-runtime-to-system-prompt architecture described above.

#### Foundational Build Requirements: Workflow Forms and Deterministic Operations

- `FR-39a`: The shared workflow-form message contract currently named `ClineWorkflowForm` in `src/shared/ExtensionMessage.ts` must be renamed to `WorkflowForm`.

- `FR-39f`: When a workflow form submission includes any value that must survive beyond form-local state, drive later next-action evaluation, or populate a later deterministic/tool-backed operation, `WorkflowRuntime` must persist the normalized submitted value through the workflow-value persistence seam defined in `FR-35a` through `FR-35m`.

- `FR-39i`: Runtime-populated selection controls, including project, folder, file, and artifact selectors, follow the same form-value persistence rule as user-entered fields. Their additional requirement is only that choices must be populated through the shared discovery/list-builder seam defined in `FR-29f` through `FR-29g`.
- `FR-39j`: Tool-backed deterministic operations that depend on workflow form input must build their payload from persisted workflow values or other runtime-owned session state after canonical next-action re-evaluation, not directly from raw form submission payloads or implicit form operation mappings.
- `FR-39k`: Workflow form transition definitions must not declare operation ids, tool ids, or implicit tool mappings. Workflow forms may collect, validate, navigate, complete, and persist declared durable values, but any later tool-backed operation must be selected by canonical next-action evaluation after form result handling completes.
- `FR-39l`: Workflow form submissions with declared `workflowValueKey` destinations must normalize every supported submitted value type into the canonical workflow-value type, including array and object submissions.
- `FR-39m`: If a submitted form value has a declared `workflowValueKey` but cannot be normalized into a canonical workflow value, runtime must fail explicitly; it must not silently skip persistence.
- `FR-40`: Rendering of the mandatory shared pre-workflow entry `WorkflowForm`, rendering of any active-step workflow form, and all user input capture must remain in the workflow form capability.
- `FR-41`: The workflow runtime must consume workflow form results as one possible next-action input and then re-evaluate the canonical next action.
- `FR-42`: When a workflow-form path requires a tool-backed deterministic operation, the workflow runtime must invoke exactly one such operation through the normal tool execution path for that next-action evaluation.
- `FR-42a`: Shared document generation for workflow-owned text artifacts is a deterministic operation class and must use the shared document-generation tool defined in `FR-20d` through `FR-20h` rather than workflow-specific document-build tools. `WorkflowRuntime` must translate workflow-module document-builder definitions into tool requests for that shared document-generation tool and invoke those requests through the normal tool execution path.
- `FR-43`: The workflow runtime must interpret deterministic results by applying the result to workflow session state and then re-evaluating the active step's module-owned next-action decision tree. On success, it must follow the module-defined success branch, including any explicit step-transition target prescribed by that branch. On failure, it must preserve failure state long enough for the module-defined failure branch to evaluate, then execute any retry branch or terminal error branch prescribed there rather than substituting ad hoc runtime-owned success/failure branching logic.
- `FR-43a`: Workflow-state-mutating tools and capabilities, including `set_workflow_values` and `workflow_progress_request`, must carry any resulting next action to the canonical post-tool next-action consumer after the tool result is recorded.
- `FR-43b`: Tool-backed deterministic operation results must feed back into `WorkflowRuntime` and then continue canonical next-action consumption; success/failure must not be handled by local tool-specific or form-specific branches.
- `FR-44`: The system must retire `WorkflowFormRuntime` as the canonical owner of per-panel workflow form payload construction.
- `FR-44a`: Generic workflow-form engine behavior may remain in the workflow form capability/runtime layer, including workflow-form session mechanics, submitted-value normalization, submitted-value validation, generic panel navigation, and shared workflow-form message-shape formatting.
- `FR-44b`: Shared pre-workflow entry `WorkflowForm` selection, workflow-specific workflow-form definition ownership, active-step workflow-form selection, per-panel payload construction, workflow-form result interpretation, and next-action orchestration must move to `WorkflowRuntime`.

#### Foundational Build Requirements: Completion, Teardown, Persistence, and Resume

- `FR-46`: The workflow runtime must evaluate completion rules after relevant workflow session mutations.
- `FR-46a`: Completion rules are completion-detection rules only. Workflow-specific follow-up work must be modeled as normal workflow steps, next-action decision actions, document builders, or tool-backed operations before completion criteria are satisfied; completion must not invoke workflow-specific completion handlers.
- `FR-48`: The workflow runtime must teardown the canonical workflow session when completion or other terminal teardown conditions are reached.
- `FR-49`: Prompt state, focus chain state, workflow-form state, entry-form state, and other workflow-related downstream surfaces must clear as a projection of workflow teardown.
- `FR-49a`: Workflow-owned values must clear as a consequence of workflow session teardown because those values are stored inside the workflow session.
- `FR-50`: The workflow runtime must own the minimum persisted workflow session state needed to resume safely and reconstruct active workflow state.
- `FR-51`: The system must retire fragmented workflow persistence ownership across placeholder-workflow fields, capability-specific workflow session blobs, and managed-workflow state.
- `FR-52`: On resume, the workflow runtime must restore workflow identity, active step, relevant progression state, and any still-relevant workflow-owned UI or deterministic state.
- `FR-52a`: When `WorkflowRuntime` tears down an active workflow session for any reason, including completion, terminal error, invalid workflow definition, invalid active step, invalid branch state, stale persisted session state, or failed resume validation, the cleared workflow state must be persisted to task metadata before workflow execution continues.
- `FR-52b`: Invalid or stale persisted workflow session metadata must fail closed on resume: `WorkflowRuntime` must reject the session, clear workflow identity, workflow session state, workflow-owned values, workflow-form state, entry-form state, focus-chain projection state, and other workflow-owned downstream projections, and the task metadata persistence layer must save that cleared state.
- `FR-52c`: A `no_op` next action must not be used as the only observable result of a workflow teardown that changed in-memory workflow state. Teardown that changes workflow state must produce an explicit runtime outcome or equivalent persistence signal that causes task metadata to be saved.
- `FR-52d`: Task-level persistence remains responsible for writing task metadata, but it must honor `WorkflowRuntime` teardown and restore-rejection outcomes by removing stale workflow metadata from disk rather than leaving invalid workflow sessions available for later resume attempts.

#### Global Requirements: Subagent Workflow Sessions

- `FR-58`: The shared workflow runtime must support concurrent workflow sessions across main-agent and child execution contexts.
- `FR-59`: When a subagent is assigned a workflow by the parent execution context, the workflow runtime must activate that workflow only in the child execution context.
- `FR-60`: A child workflow session must have its own `activeWorkflowName`, workflow session state, active step, prompt projection, native tool schema projection, progression, completion, and teardown state.
- `FR-61`: Parent workflow state must remain unchanged by child workflow activation unless explicitly coordinated by a higher-level application behavior outside this runtime scope.
- `FR-62`: The subagent runner must not become a separate workflow orchestrator; it remains the caller/bootstrap seam for child execution contexts.
- `FR-62a`: A child workflow session may initialize selected workflow values from the parent workflow session only when the active child workflow definition explicitly declares those inheritance rules.
- `FR-62b`: Parent-to-child workflow-value inheritance must initialize only the child session's workflow-value map and must never replace, alias, or mutate the parent session's workflow-value map. For the foundational build, inherited object/array values are permitted only as read-only shared context or as values that parent and child are not expected to mutate independently; workflow modules must not declare object/array inheritance for values that require independent parent/child mutation isolation.
- `FR-62c`: The system must support same-key inheritance semantics where a child workflow value is initialized from the parent session value for that same key when the workflow definition explicitly declares that mapping. Same-key inheritance is initialization only and must not imply ongoing synchronization between parent and child values.
- `FR-62d`: The system must not introduce a dedicated locking, serialization, or anti-collision subsystem for same-project parent/subagent workflow activity as part of this initiative.
- `FR-62e`: Child workflow project selection is copied from the parent workflow session as runtime activation context, not through the workflow-value inheritance map and not through a child-rendered workflow form.
- `FR-62f`: The subagent runner must reject direct subagent-emitted `use_skill` tool calls; subagent workflow activation must happen before the child agent turn through parent-owned assignment/bootstrap.
- `FR-62g`: Parent-owned subagent workflow assignment may be expressed in the parent-authored subagent prompt only through `use_skill("workflow-name")`, `use_skill('workflow-name')`, `skill_name = "workflow-name"`, or `skill_name = 'workflow-name'`.
- `FR-62h`: Subagent workflow assignment markers are bootstrap metadata consumed by `SubagentRunner` before the child agent turn; they must not be treated as child-authored `use_skill` tool calls.
- `FR-62i`: Subagent workflow assignment must resolve through the product-owned workflow registry before activation. Zero markers mean no workflow assignment and normal subagent execution. If one or more markers are present but cannot be honored, including multiple distinct marker names, an unresolvable workflow name, missing or incomplete parent workflow/session/project context, activation returning `no_op`, or activation producing a child-invalid next action, `SubagentRunner` must fail the subagent run before the first child model request and return a failure result with the cause when available.
- `FR-62j`: Subagent workflow assignment parsing must remain limited to the explicit markers in `FR-62g`; the runtime must not infer workflow assignment from general prose, prompt-visible skill listings, or child-agent tool output.
- `FR-62k`: Parent-assigned child workflow activation must consume the activation next action in the child execution context before the first child prompt assembly.
- `FR-62l`: In child execution, a model-driven handoff next action means child workflow prompt/tool projection is ready for the next child model turn; it is not a UI action.
- `FR-62m`: Child workflow tool-backed operations must execute through the same child tool-handler path used for model-authored child tools, including workflow-projected tool availability, then feed the result back into `WorkflowRuntime` and continue canonical next-action consumption.
- `FR-62n`: `SubagentRunner` must strip explicit `FR-62g` assignment marker snippets from the child prompt before constructing the initial child user message.
- `FR-62o`: Failed subagent workflow assignment must not be represented as child-visible system-prompt instructions, user-prompt instructions, prompt-visible skill assignment text, or fallback `use_skill` guidance.
- `FR-62p`: Assignment marker names must not be used to filter or narrow child prompt skill exposure. Prompt skill exposure must use configured subagent skills when present, or normal available-skill discovery when absent.
- `FR-62q`: A successfully activated child workflow may affect child prompt/tool projection only through `WorkflowRuntime` child-session activation and canonical next-action consumption.

#### Global Requirements: Validation, Diagnostics, and Error Handling

- `FR-63`: The workflow runtime must validate workflow definitions before using them for orchestration.
- `FR-63a`: Foundational workflow-definition validation must cover runtime-owned structural contracts and workflow-value inventory references used by runtime-owned operations; it must not treat module-owned native tool schema contents as a foundational runtime validation source during prompt/tool projection.
- `FR-64`: The workflow runtime must provide shared error handling for activation, projection, deterministic operations, progression, completion, teardown, persistence, and resume paths.
- `FR-65`: When deterministic resolution fails, the workflow runtime must execute the retry branch defined by the active workflow and step in the module-owned next-action decision tree. If that retry path reaches terminal failure, the workflow runtime must execute the module-defined final user-visible error branch and surface that final error message to the user.
## 4. External Interface Requirements

### 4.1 User Interfaces

- `IR-1`: The system must project workflow step and status information to focus chain as a downstream UI surface.
- `IR-2`: The system must support one mandatory shared pre-workflow entry `WorkflowForm` that runs for every workflow invocation.
- `IR-3`: The system must support workflow-form payloads for both the mandatory shared pre-workflow entry `WorkflowForm` and any active-step workflow form, with all such payloads rendered by the existing workflow form capability.
- `IR-3a`: The user-facing mandatory shared pre-workflow entry `WorkflowForm` must provide an informational first panel plus a project-selection second panel that can choose `new` versus `existing`, select an existing project derived from per-project folder names beneath the visible project output root, and provide a new project title when needed.
- `IR-4`: User-facing workflow progression approval flows must continue to operate through existing tool/UI mechanisms, but canonical progression must occur only through workflow runtime validation and state mutation.
- `IR-5`: Workflow completion and teardown must clear workflow-owned downstream UI surfaces so the user no longer sees stale active-workflow state.

### 4.2 Hardware Interfaces

- `IR-6`: The workflow runtime introduces no dedicated hardware interface requirements beyond the existing supported extension host and user workstation environment.
- `IR-7`: The design must remain compatible with the current local-development and extension-execution environment used by the repo.

### 4.3 Communications Interfaces

- `IR-8`: The workflow runtime must operate within the existing in-process extension backend/runtime architecture and must integrate through the existing backend, webview/UI, persistence, and normal tool-execution seams rather than introducing a new orchestration transport.
- `IR-9`: The workflow runtime must not require a new standalone remote service or a new communications protocol to perform workflow orchestration.

### 4.4 Software Interfaces

- `IR-10`: The workflow runtime must integrate with `task/index.ts` for workflow activation and per-turn orchestration entry.
- `IR-11`: The workflow runtime must integrate with the system prompt architecture by projecting workflow prompt data and workflow-owned native tool schema for final prompt assembly.
- `IR-12`: The workflow runtime must integrate with focus chain by providing runtime-owned workflow step and status projections.
- `IR-13`: The workflow runtime must integrate with the workflow form capability by providing per-panel payloads and consuming returned results.
- `IR-15`: The workflow runtime must integrate with the normal tool execution path for tool-backed deterministic operations, while keeping direct runtime-owned deterministic procedures inside `WorkflowRuntime` or shared runtime-owned seams.
- `IR-16`: The workflow runtime must integrate with the persistence layer for workflow session save and resume behavior.
- `IR-17`: The workflow runtime must integrate with subagent execution contexts such that each context can host its own workflow session under the same shared runtime implementation.
- `IR-17a`: The workflow runtime must integrate with the AI-callable workflow-value persistence seam such that model-authored writes and backend-authored writes are applied through the same workflow session state contract.

## 5. Non-Functional Requirements

### 5.1 Performance Requirements

- `NFR-1`: Workflow activation, workflow definition resolution, and projection of prompt/tool/UI state must occur within the normal turn lifecycle and must not require a separate orchestration turn.
- `NFR-2`: The architecture must eliminate runtime reliance on placeholder substitution, markdown workflow parsing, and file-dependent workflow resolution for shipped in-scope workflows.
- `NFR-3`: When deterministic workflow execution requires a tool-backed deterministic operation, the workflow runtime must use the existing normal tool execution path rather than creating an additional execution stack. Deterministic workflow behavior that does not require tool-governed execution must not be forced through a tool call.
- `NFR-4`: Concurrent parent and child workflow sessions must remain isolated so that orchestration work in one execution context does not corrupt another session’s state.
- `NFR-4a`: Parent and child workflow sessions must not share one mutable workflow-value map.
- `NFR-4b`: The architecture must not introduce a dedicated locking, serialization, or anti-collision subsystem for same-project parent/subagent workflow activity as part of this initiative.

### 5.2 Safety Requirements

- `NFR-5`: The workflow runtime must validate whether a progression or deterministic action is allowed for the active step before mutating canonical workflow state.
- `NFR-6`: The workflow runtime must not leave stale workflow UI, prompt state, or persisted session state behind after teardown.
- `NFR-7`: Resume behavior must fail safely when persisted workflow session state is invalid, stale, or incomplete.
- `NFR-7a`: Filesystem-safe project-identity normalization must remove or replace invalid filesystem characters, trim leading and trailing whitespace, collapse internal whitespace into a single separator, normalize casing consistently, collapse repeated separators, and reject any input that would normalize to an empty filesystem identity.
- `NFR-7b`: Invalid workflow resume attempts must be idempotent: after the first rejection and persisted cleanup, subsequent task loads must not reattempt the same invalid workflow session.

### 5.3 Security Requirements

- `NFR-8`: Workflow state and workflow-owned projections must remain scoped to their execution context so that child workflow activation does not leak or overwrite parent workflow state.
- `NFR-8a`: Explicit parent-to-child workflow-value inheritance must initialize only workflow-definition-approved values and must not create implicit broad inheritance of all matching keys or ongoing parent/child value synchronization.
- `NFR-9`: Product-owned in-scope workflows must be resolved from trusted runtime code rather than from user-authored workflow assets.
- `NFR-10`: Workflow orchestration must continue to execute tool-backed operations through the existing generic tool-execution controls, including tool registration/execution gating, strict-plan-mode restrictions, approval and auto-approve handling, hooks where applicable, and existing workspace/path boundary checks. File-accessing workflow tools and runtime-invoked workflow capabilities must not bypass those controls through bespoke workflow-specific execution paths.

### 5.4 Software Quality Attributes

- `NFR-11`: The architecture must improve maintainability by concentrating workflow orchestration in one shared runtime and concentrating workflow-specific behavior in workflow modules.
- `NFR-12`: The architecture must improve extensibility so that adding a new shipped workflow primarily means registering a new workflow module against the shared runtime contract.
- `NFR-13`: The architecture must improve reliability by giving workflow identity, active step, progression, completion, and resume one canonical owner.
- `NFR-14`: The architecture must preserve separation of concerns by keeping final prompt assembly, UI rendering, and generic tool execution in their specialist capabilities.
- `NFR-15`: The architecture must support behavioral parity migration by allowing the runtime to represent prompt content, native tool schema, deterministic rules, workflow forms, and completion rules on a per-workflow basis.
### 5.5 Other Requirements

- `OR-1`: The implementation plan derived from this document must account for migration away from placeholder workflows, BMAD support files, managed workflows, and fragmented workflow state without losing shipped workflow behavior.
- `OR-1a`: The implementation plan must trace the workflow-value contract end to end, including backend-owned writes, AI-callable writes, subagent inheritance rules, persisted session state, and teardown clearing behavior.
- `OR-2`: The implementation plan must include verification of activation, progression, deterministic resolution, workflow-form integration, completion, teardown, persistence, resume, and subagent isolation behavior.
- `OR-3`: The target architecture must remain an in-process backend capability and must not be re-scoped into a separate service as part of this initiative.
