# Correct Course Workflow Module Action Plan

## FrontMatter

- Read this plan from top to bottom before making any changes.
- Read each task and subtask in full immediately before executing it.
- Execute only one task or subtask at a time- return to this file and read the next task or subtask before executing. Do not rely on your internal memory when switching to a new task or subtask.
  - Exception: You may execute multiple sequential subtasks with one patch only if they are scoped to the same file, but must review each subtask vs the landed code after the patch to ensure that every subtask was implemented exactly as prescribed before marking the subtask as complete.
  - After completing a task or subtask, update that step's checkbox from "[ ]" to "[x]".
- Checkbox updates to this plan file are allowed in every step in addition to the listed allowed-files set.
- Do not edit any file not listed in the current step's allowed-files list.
- If any ambiguity is discovered, or if any change is needed outside the allowed-files list for the current step, stop and ask the user before proceeding.
- Implement tasks and subtasks exactly as instructed. If deviation seems necessary, stop, inform the user, and explain why you believe the task or subtask should be carried out differently than prescribed.
- You must avoid these banned development bad habits:
  - "any" typing
  - val as SomeType
  - as any in tests
  - optional properties most of the time (explicitly model which combinations exist and which don't whenever possible)
  - one-letter generics
  - non-boolean boolean checks
  - bang bang operators (explicitly check for the condition instead)
  - != null (explicitly check for the condition instead)
  - not declaring function return types
  - abuse of type assertions (use them only in special scenarios where the type is clearly known, and give priority to type declarations, interfaces, or generics)
  - Failing to use utility types (use utility types such as partial, pick, omit, etc when appropriate)
  - forcing assertions when types don't match
  - not using enums to manage constants
  - not using generics to abstract duplicated code
  - not using type narrowing
  - not explicitly defining generics parameters

## Scope

Build the product-owned `correct-course` workflow module from the approved requirements. The module must resolve the required architecture prerequisite, collect issue and source context through one multi-panel workflow form, use runtime-owned JSON-backed workflow-form option loading for epic and story choices, allocate and initialize one project-numbered `change_management_plan` artifact, project the exact approved Step 3 prompt with materialized workflow values and conditional source blocks, expose only the approved per-turn model-facing tool schemas, register the workflow, and add focused unit and prompt-projection tests.

## Scope Boundary

Do not register `correct-course.md` or any `.md` alias. Do not add child/subagent activation. Do not add AI-writable workflow values. Do not create a specialized backend workflow tool. Do not create module-owned registry/static-data files. Do not modify shared runtime, shared workflow-form, artifact-family, project-numbering, or JSON options infrastructure. Do not expose `build_workflow_document`, `create_workflow_artifact`, `archive_workflow_artifact`, `delete_workflow_artifact`, `move_workflow_project_file`, `update_story_index_status`, story-planning tools, web tools, MCP tools, `use_subagents`, `ask_followup_question`, `workflow_progress_request`, `set_workflow_values`, or retired tools in correct-course model-facing tool schemas.

## Known Issues/ Risks/ Technical Debt

- This action plan depends on the already-landed runtime support for `WorkflowArtifactFamily.ChangeManagementPlan` with `numberingScope: "project_numbered"`.
- This action plan depends on the already-landed runtime support for `jsonOptionsSource.sourceFileDiscovery` to aggregate story dropdown options from multiple selected-project story index files.
- Correct-course Step 1 uses runtime-routed workflow-form continuation plus module-owned selected-project file availability predicates derived from the runtime-resolved `architecture_document` prerequisite path, matching the module build guide's selected-project file-check routing guidance.
- If `npm run check-types` fails before TypeScript checking because generated proto files are missing or host probing fails, run `npm run protos` and rerun the exact blocked validation command before treating the failure as a code defect.
