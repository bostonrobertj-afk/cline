# Quick Dev Workflow Module Requirements

## Scope

These requirements define the runtime workflow module for the Quick Dev workflow. The module must implement the source workflow at `/Users/robertboston/Documents/Cline/Workflows/quick-dev.md` within the workflow-runtime module system.

The module must carry forward applicable runtime workflow requirements from `docs/workflows/workflow-runtime/requirements.md` and must follow the implementation constraints in `docs/workflows/workflow-runtime/workflow-modules/module-build-guide.md`.

The source workflow document is a migration source of truth only. The runtime module must not read, import, or depend on the source markdown file, legacy `.cline/workflow-config.yaml`, legacy prompt files, or any legacy workflow assets at runtime.

Quick Dev is an implementation workflow. It does not produce a workflow-owned document. It consumes a required Quick Spec implementation spec generated by the `quick-spec` workflow, implements one confirmed implementation phase from that spec, and then relocates the consumed Quick Spec artifact to the selected project's `review` subfolder.

## Source Wording Preservation

All user-authored source wording identified in these requirements must be preserved exactly in runtime prompts and user-visible workflow metadata, except for supported workflow token rendering. The implementation must not rewrite, summarize, or stylistically recast the required prompt text.

The source document's authoring labels, including `# Tool Schema Override`, `# Focus Chain Tasks`, `### Prompt`, and `### Progression Rule`, are not AI-facing prompt content and must not appear in rendered model prompts.

The Step 3 source procedure text is not AI-facing prompt content. It must be represented as deterministic workflow routing.

The prompt token `{workflow.spec_file}` must remain in the runtime prompt templates and must be rendered only by the shared workflow prompt renderer. Prompt code must not use local string replacement for workflow values.

## Runtime-Owned Values

The Quick Dev module must declare every supported workflow value key in `workflowValueKeys`, per the runtime workflow value requirements.

The module must declare `entryProjectValueKeys` with exactly these three destinations, and each destination must also appear in `workflowValueKeys`:

- `projectMode`
- `projectTitle`
- `projectFolderName`

The module must include a workflow value key named `spec_file`. This value must hold the absolute path to the selected Quick Spec prerequisite file after runtime-owned prerequisite resolution succeeds.

The module must include a workflow value key named `spec_file_filename`. This value must hold the basename of `spec_file` and must equal `quick-spec.md`. It is required because the runtime-owned `move_project_file` action accepts a filename workflow value, not an absolute path workflow value.

No other Quick Dev workflow value keys are required by the source workflow. Additional workflow values must not be added unless a later requirements revision explicitly authorizes them.

The Quick Dev module must not define AI-writable workflow values, and no Quick Dev step may expose `set_workflow_values`.

Workflow values must remain JSON-safe, must be cleared during workflow teardown, and must participate in runtime-owned session resume behavior.

## Required Prerequisite File

The Quick Dev workflow requires one selected-project prerequisite file before model-driven work can begin:

| Prerequisite id | Requirement | Producing workflow | Project subfolder | Match | Workflow value key | Output document reference |
| --- | --- | --- | --- | --- | --- | --- |
| `spec_file` | required | `quick-spec` | `planning` | exact filename `quick-spec.md` | `spec_file` | `none` |

The prerequisite must be declared in `WorkflowDefinition.prerequisiteFiles` and resolved through the runtime-owned `resolve_prerequisite_files` decision action.

The prerequisite declaration must use:

- `id`: `spec_file`
- `requirement`: `required`
- `producingWorkflowName`: `quick-spec`
- `projectSubfolderSegments`: `["planning"]`
- `match.kind`: `exact_filename`
- `match.filename`: `quick-spec.md`
- `workflowValueKey`: `spec_file`
- `outputDocumentReference`: `none`

The prerequisite file is the singleton project artifact produced by the already-built Quick Spec workflow. The producing workflow owns `WorkflowArtifactFamily.QuickSpec`, the singleton identity `quick_spec`, and the filename `quick-spec.md`. Quick Dev must consume the selected prerequisite path only; it must not allocate, initialize, rebuild, rename, or overwrite the Quick Spec artifact as workflow-owned output.

Prerequisite discovery must resolve only under the selected project root and must target the selected project's `planning` subfolder. It must not accept absolute paths supplied by the model, parent-directory escapes, or files outside the selected project.

After prerequisite selection succeeds, runtime/module logic must derive `spec_file_filename` from the basename of `spec_file` and validate that it is exactly `quick-spec.md` before any model-driven work or later file relocation can proceed.

If `spec_file` is missing or blank when deterministic setup runs, the workflow must fail with this exact terminal error message: `No implementation specs were found in the selected project folder. You can generate one by running the Quick Spec workflow.`

If `spec_file` is present but its basename is not exactly `quick-spec.md`, the workflow must fail with this exact terminal error message: `A file with the required naming conventions was not located. Please ensure that there is a spec file generated by the Quick Spec workflow in the selected project's folder with naming convention "quick-spec.md"`

If no required `quick-spec.md` file is discoverable, if the selected path does not derive `spec_file_filename: "quick-spec.md"`, or if the user rejects or cancels prerequisite selection, the workflow must not proceed to model-driven phase review, implementation, staging, commit, project-record update, or completion.

## Runtime Artifacts And Output Documents

Quick Dev must not define workflow-owned artifacts.

Quick Dev must not define a document builder, output document value, artifact allocation route, artifact initialization route, `build_workflow_document` action, or any module-owned document template.

Any implementation-file edits are model-driven work performed through allowed model-facing file tools during Step 2. They are not workflow-owned artifacts.

The Step 3 relocation of `quick-spec.md` is a deterministic runtime file lifecycle move of a consumed prerequisite file. It must not be implemented as artifact allocation, document generation, or a model-facing file edit.

## Steps

The workflow must define exactly three steps:

| Step id | Order | Name | Purpose |
| --- | --- | --- | --- |
| `step-1` | 1 | `Review Assigned Phase` | Resolve the required Quick Spec file, have the agent identify the first incomplete phase, obtain user confirmation, and progress with `workflow_progress_request`. |
| `step-2` | 2 | `Implement Assigned Phase` | Implement only the confirmed phase, stage and commit the phase changes, then progress to Step 3 with `attempt_completion`. |
| `step-3` | 3 | `Update Project Records` | Relocate the consumed `quick-spec.md` file from the selected project's `planning` subfolder to the selected project's `review` subfolder, then end the workflow. |

No additional Quick Dev steps may be added unless a later requirements revision explicitly authorizes them.

## Step 1 Routing

After the shared selected-project entry form is submitted, Step 1 must first run the runtime-owned required-prerequisite resolution for `spec_file`.

If required-prerequisite resolution succeeds, Step 1 must route to a `project_prompt` action that renders the Step 1 prompt with `{workflow.spec_file}` materialized from the resolved `spec_file` workflow value.

If the agent calls `workflow_progress_request` and the user confirms it, the workflow must transition to Step 2 and render the Step 2 `project_prompt`.

If the user denies the `workflow_progress_request`, the workflow must remain in Step 1 and render the Step 1 `project_prompt` again.

Step 1 must not route directly to workflow completion.

## Step 1 Prompt

Step 1 must render this exact AI-facing prompt text:

```text
You've been called within a workflow designed to implement one phase within a small project based on documentation built in an upstream workflow. Follow the instructions provided for each step exactly. You will receive additional instructions as you complete steps and unlock additional steps in the workflow.

Read this first: `{workflow.spec_file}`
Identify the first incomplete phase in the file, and ask the user to confirm that they'd like you to implement that phase during this workflow. Once they've confirmed, analyze that phase only to build an understanding of the work to be performed. Identify any ambiguities or internal conflicts within the file, and notify the user if any are present.
Once you've read the assigned phase and ensured it is free of internal conflict or ambiguity, send a message to the user informing them that the file is in a good state for execution, and that you will be initiating progression to the execution phase. When the user responds, use workflow_progress_request to progress this workflow to the task execution phase.
```

The rendered prompt must include the resolved prerequisite file path in place of `{workflow.spec_file}`. It must not include the literal token after rendering.

The prompt must not include the source authoring line `### Progression Rule: user confirmation via workflow_progress_request`.

## Step 2 Routing

Step 2 must route to a `project_prompt` action that renders the Step 2 prompt.

If the agent calls `attempt_completion` successfully, the workflow must route to Step 3. It must not route directly to `complete_workflow`.

Step 2 must not expose `workflow_progress_request`, and no Step 2 route may transition anywhere except Step 3 after successful `attempt_completion`.

Staging and committing phase implementation changes are model-driven responsibilities expressed in the Step 2 prompt and performed through `execute_command`. Quick Dev must not implement deterministic runtime staging or commit finalization behavior.

 If any task or subtask is ambiguous, internally contradictory, references a missing symbol, requires a change outside the authorized scope for the assigned phase, or cannot be implemented compile-safely as written, stop and report the blocker instead of improvising.

Once all of the assigned phase's tasks and subtasks are complete, stage the files revised, deleted, or generated during implementation. Include the file name and phase number in the commit description.

 After committing your changes, stop and use attempt_completion to provide the user with an implementation summary including:
 - phase completion status
 - any blocker or failed validation, with exact output (if applicable)
 - files changed
 - validation commands and results (if applicable)
 - confirmation that no later-phase work was performed

## Step 3 Routing

Step 3 must not render an AI-facing prompt.

Step 3 must not expose a model-facing tool schema.

Step 3 must run exactly one deterministic file lifecycle action: `move_project_file`.

The Step 3 `move_project_file` action must use:

- `sourceFolderSegments`: `["planning"]`
- `destinationFolderSegments`: `["review"]`
- `filenameWorkflowValueKey`: `spec_file_filename`

The move must relocate the selected project's `planning/quick-spec.md` file to `review/quick-spec.md` and must preserve the filename exactly.

After the `move_project_file` action succeeds, the workflow must route to `complete_workflow` and end.

If the `move_project_file` action fails, the workflow must route to `terminal_error` with this exact terminal error message and must not complete: `migration of the completed spec to the project's review subfolder failed. Please manually relocate the file.`
